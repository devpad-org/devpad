# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Run all commands from the repository root unless noted.

| Task | Command |
|------|---------|
| Full build | `make build` |
| Backend build only | `make backend` |
| Frontend install | `make install-frontend` |
| Frontend build + type-check | `make frontend` |
| Frontend type-check only | `cd frontend && npm run type-check` |
| Theme check (also run by `npm run build`) | `cd frontend && npm run check-themes` |
| Backend dev server | `DEVPAD_ENCRYPTION_KEY=<key> go run .` (required; make one once with `openssl rand -hex 32` and reuse it) |
| Frontend dev server | `make dev-frontend` |
| Format all Go files | `make fmt` |
| Check Go formatting (also run by `make test`) | `make fmt-check` |
| All Go tests with coverage | `make test` |
| All Go tests without coverage | `go test ./...` |
| Package tests | `go test ./internal/auth` |
| Single Go test | `go test ./internal/auth -run '^TestService_LoginLogout$'` |
| Agent tests | `go test ./cmd/agent` |

`make build` is the correct full build path: it builds the Vue frontend into `web/dist/`, builds `cmd/agent`, copies the embedded agent binary and Dockerfile into `internal/agentbin/` and `internal/dockerfile/`, then builds `bin/devpad`. The Vite dev server proxies `/api` to `http://localhost:8080`, so run it alongside the backend dev server.

## Architecture

Devpad is a Go web server that serves an embedded Vue 3 IDE frontend and manages Docker-backed workspaces. `main.go` reads flags/env vars, builds `server.Config`, and delegates application assembly to `internal/server`.

**Composition root** — `internal/server/server.go` opens SQLite, runs embedded migrations, creates the encryption cipher, wires auth/settings/workspace/admin/AI/preview services and handlers, registers all `net/http` `ServeMux` routes, applies auth middleware and body limits, routes preview subdomains by host, and serves `web.Handler()` as the SPA fallback. With `--domain`, TLS is configured via CertMagic/Cloudflare DNS-01; without it, the server listens on plain HTTP.

**Backend layout** — domain packages under `internal/`: handlers translate HTTP to service calls, services own business logic, and repositories own SQLite access. Key packages: `internal/auth`, `internal/settings`, `internal/workspace`, `internal/wsservice`, `internal/admin`, `internal/preview`. Prefer the narrow interfaces already defined in each package (e.g. `internal/workspace/interfaces.go`).

**Workspace execution** is split between the host and an in-container agent. The host uses the Docker SDK through `internal/container.Manager` to build/run `devpad-workspace:latest`, create per-workspace Docker volumes and networks, inject SSH material, and manage sidecar containers. `cmd/agent` is built as `bin/devpad-agent`, embedded into the main binary, and runs inside each workspace container at port 9100. Host workspace handlers proxy terminal, file watching, file operations, commands, and Git operations to the agent over HTTP/WebSocket using a per-workspace auth token.

**Projects and workspaces** — every new workspace belongs to a project (`internal/project`): either its one project workspace (`kind = 'interactive'`, the user's IDE for the project) or an AI sandbox (`task`/`review`, each owning one branch). Each project's canonical bare repo lives in an isolated repo container; devpad moves commits between it and workspaces with git bundles over the agent channel, and no project-linked workspace gets a mount, route or credential to that repo or the user's SSH keys. A project's protected branches, its default branch plus `projects.protected_branches` (such as `main` in a project that works on `develop`), move only through merge requests: no sandbox owns one, the project workspace never publishes one, merge requests target only them, and only they are pushed upstream. Only the user deletes a branch, from the project's Branches dialog (`DeleteBranch`, under the branch lock and holding the branch as a publish does): never a protected one, one a sandbox owns, an open merge request's source, or one a task not merged or cancelled works on or starts from. Each `BranchGuard` runs the deletion under the lock that opening merge requests or creating tasks takes, so its answer still holds when the branch goes; `git push devpad :<branch>` is refused. `SetBranches` protects a branch under the same lock as sandbox and publish reservations, which re-read the project's branches. Workspaces without a project are left from before projects: devpad no longer creates them, and they can only be used, converted into a project, or deleted.

**Project environments and setup** — a project's environment is the body of a Dockerfile (no `FROM`, `ADD` or `COPY`: the daemon fetches `ADD` URLs on the host's network and `COPY --from` reads any local image) that `internal/project/environment.go` builds in the background on `devpad-workspace:latest`, inside a frame devpad owns (agent entrypoint, `devpad` user, `/workspace`), into `devpad-project-<id>:<hash>`, where the hash covers the base image ID and the Dockerfile. Builds run on a network of their own with memory, CPU and time limits and no build context. New workspaces get the last image that built (devpad's image before any has); the repo container always keeps devpad's image; the project workspace moves to a new image only when the user rebuilds it, which keeps only `/workspace`. The setup script (`internal/project/setup.go`) then runs once in each newly seeded workspace, and task and review agents start only after any environment build and their sandbox's setup have finished, waiting outside their locks. A project's services (`project_services`, kept by `internal/wsservice`) are sidecars every new workspace of the project gets its own fresh copy of, never one shared with another workspace: `workspace.create` provisions and starts them before the container, so their connection variables are in its environment, without waiting for them. A newly seeded workspace's setup run is recorded `pending`, and a background preparation (which `project.AwaitSetup` waits on for a sandbox, outside the launcher's locks, and `Reconcile` resumes) waits for each service to pass its Docker health check (`definition.healthcheck`) before starting the script, so it finds them ready. A workspace stopped meanwhile keeps its run pending (a task starts its sandbox again and waits once more; starting the project workspace again resumes it); a sandbox whose services never get ready fails its task or review with `ErrServicesNotReady`, the project workspace's run is recorded as failed, and `AwaitEnvironment` pulls their images before the sandbox is made under any lock. A project keeps the user's acceptance of a service's licence terms, and a copy is refused (`ErrLicenseOutdated`) once the terms' `License.version` has moved past it. The project workspace gets services added to the project later when it is rebuilt or the user adds them from the Project page (`POST /api/projects/{id}/workspace/services`, `workspace.ProvisionProjectServices`, under the workspace's lifecycle hold so never beside a rebuild; `workspace_services` is unique by workspace and type), and the project workspace's services panel offers to add its own services to the project (`.../services/adopt`). A workspace's container environment names every service with a container, stopped ones too, and lists their variables' names in `DEVPAD_SERVICE_VARS`. A container's environment is fixed when it is made, so devpad also sends a running workspace's agent the variables of every service it has (`SyncServiceEnv`: on start, restart, and adding, starting or removing a service), and the agent puts them over the container's own in every terminal and command it starts (`processEnv`), keeping them in `~/.devpad/service-env.json` across restarts; once synced, it drops the container's own variables of services since removed. `wsservice.PromptProvider` tells each run the variable names, never the values.

**Pipelines** — `internal/pipeline` reads a project's CI pipeline: `.devpad/pipeline.yml` (or `.yaml`, never both), named jobs each with a bash `run`, an optional `timeout` (10m by default, 1s to 1h) and the project `services` it gets fresh copies of. `Parse` refuses anything it doesn't know, saying on which line. `Resolve` reads the file at a full commit hash (`ReadAt`); a commit without one uses the project's `pipeline_config`, which only the user sets (`PUT /api/projects/{id}/pipeline`: the pipeline package validates it, the project stores it as it is), and a file that doesn't parse makes the pipeline `Invalid`, never a reason to use the setting. `Resolved.Hash` is of the jobs (`JobsHash`), so rewriting the YAML without changing them keeps it; an `Invalid` pipeline's is of its YAML. A merge request's pipeline is to come from its target branch, never the change. `projects.pipeline_branches` are the protected branches that run it, set through `SetBranches` like `auto_merge_branches`. What a run is to be made of: `project.PinPipeline` has the repo container pin what a pipeline tests to `refs/devpad/pipelines/<id>` (`internal/pipelineid` is the id rule; `cmd/agent/repo_pipeline.go`: a commit, or the trial merge of a source onto a target through the `mergeTree` merges use, so the tree a merge, squash or fast-forward lands; it moves no branch, runs no hook and reads no attributes from content, and a conflict is an answer, `Conflict`, that also drops the id's earlier pin), `PipelineBundle` bundles it (held to `gitbundle.MaxBytes`, the agent's own cap, on the host, since no agent receives it) and `DeletePipelineRef` drops it. Jobs use `container.JobRuntime`, a narrow interface the Docker manager also implements (`container.Docker`): each job is to get its own network (`CreateJobNetwork`, which devpad never joins; `ErrNoNetworkPool` when Docker has no address pool left, which passes), fresh copies of its services (`wsservice.StartJobServices`: the licence and architecture checks and health wait, `DefaultJobServiceLimits`, no `workspace_services` rows, each reachable by its type) and a container from the project's image (`StartJobContainer`: only `sleep` for its lifetime under Docker's init, as `devpad` with `no-new-privileges` and no capabilities, so no sudo and tools belong in the environment, `DefaultJobLimits`, no restart, nothing of devpad's in its environment, and its files, such as the bundle, put in before it starts, never after). `ExecJob` runs a command there and reads its exit code and an out-of-memory kill from Docker, which cannot stop an exec, so a context that ends kills the whole container; `JobScript` runs a job's script with `-eo pipefail` in a login shell's environment but not as one, whose `~/.bash_logout` would turn `exit 0` into 1. Everything a job makes carries `devpad.pipeline`/`devpad.job` labels and a `devpad-job-<id>.<job>` name, and `RemoveJobResources` removes only what has both, so cleanup also finds what a cancelled create or an earlier process left but never a container whose image carried the labels. Nothing runs pipelines yet.

**The devpad git remote** — a project workspace's repo has a `devpad` remote (`devpad::project`) served by `git-remote-devpad`, the agent binary linked under that name. The helper talks to the agent over a unix socket; `internal/gitbridge` long-polls each running project workspace's agent for those requests and answers them through the project service. `git fetch devpad` refreshes `refs/remotes/devpad/*` by bundle, and `git push devpad <branch>` is only a request: devpad pulls the branch and publishes it exactly like the Publish button (never a protected branch, never a sandbox-owned branch, fast-forward only), and the IDE shows each push. The IDE assistant runs in the same workspace and can push this way too, with no more power than the Publish button. When the project has an upstream, the workspace also has an `origin` remote (`devpad::upstream`), a read-only view of it: listing it makes devpad sync from the upstream (`internal/project/upstream.go`: fetch into the canonical repo's `refs/upstream/heads/*`, then fast-forward only protected branches that are strictly behind; never create, delete or force), fetching it brings those refs as `refs/remotes/origin/*`, and pushing to it is refused. `git fetch devpad` also syncs when the last sync is over a minute old. Syncs are shared per project and only ever asked for, never shaped, by the workspace. Local branches track `devpad/<branch>` and `remote.pushDefault` is `devpad`, so a plain `git pull` and `git push` work. Sandboxes and standalone workspaces are never polled, so the helper refuses there. The agent is inside the workspace and so hostile: every limit on the work a workspace can make devpad do (poll pacing, response size, requests and fetched branches per minute, log lines) is enforced in `internal/gitbridge`, never in the agent.

**Workspace previews** — `internal/preview` generates one-time preview URLs. Preview subdomains follow `{workspaceID}-{port}.preview-domain` format; traffic is reverse-proxied through the workspace agent's port proxy after token/cookie validation. Each preview has its own host-only `__Host-` cookie and stands alone: because previews are same-site with each other, the proxy (`refusesCaller`) refuses every same-site or cross-site request (by `Sec-Fetch-Site`, or by `Origin` for a client without it) that isn't a top-level navigation, including from the same workspace's other ports. A frontend reaches its API through its dev server's proxy, and devpad never answers CORS for an app. The app sees the agent's address as `Host`: the proxy sends `X-Forwarded-Host`/`-Proto` and rewrites redirects to that address.

**SQLite migrations** live in numbered `.sql` files under `internal/database/migrations/`. `database.Migrate` applies them lexicographically and records versions in `schema_migrations`. Always add the next numbered migration; never edit an applied one.

**AI subsystem** is intentionally layered. `internal/ai` is only the composition facade. Domain types live in `internal/ai/domain`, use cases in `internal/ai/app`, persistence in `internal/ai/storage`, provider adapters in `internal/ai/provider/*` (Anthropic, Mistral, Minimax, Moonshot, OpenAI-responses), workspace tool execution in `internal/ai/tools`, and HTTP/SSE transport in `internal/ai/transport/http`. Other packages add workspace-specific tools as an `aitools.ToolProvider`, whose `Contribute` gives a run its tools and system-prompt context (sections ordered by `Rank`, then by when the provider was added), and which can require the user's approval for some calls (`ApprovalGate`). Providers never work out for themselves what a run's workspace is: `internal/runscope` resolves an `aitools.Scope` (user, workspace, kind, project, sandbox branch, and the open task, the pending review or the task's open merge request a sandbox is there for) once when a run starts, where failing to resolve it fails the run, and again for each call a provider might own, so a provider checks `req.Scope`, not what it offered at the start. `internal/mergerequest` gives review agents their review tools (an auto-fixing review, as automatic reviews of a task's merge request are, sends requested changes to the task's agent and reviews the commits it answers with, up to `maxReviewRounds` reviews, the last of which waits for the user; a project's `auto_merge_branches`, protected branches set with `SetBranches`, are those a task's merge request merges into once a review agent's approving run completes (one that fails or is stopped never merges), only while that review is the latest, of the head, with the target still at its `target_sha` (which the repo agent checks as it merges, `ExpectedTargetSHA`), no blocking thread open and the task in review; `merge_request_reviews.run_settled` records that devpad has settled a submitted review's run, and `Reconcile` settles those a restart left: no agent has a merge tool, devpad checks this itself under the merge request's lock, and an automatic merge never pushes upstream), and `internal/projecttools` gives the assistant in a project workspace the board (list, create and start tasks, read, comment on and open merge requests: opening one needs the user's approval, names its protected target explicitly, and never takes an unfinished task's or a sandbox's branch). `task.CommentTools` lets a task's agent comment on its own task and the assistant on any of the project's; each author edits only its own comments, triggers keep every version (`task_comment_revisions`), and an agent's comment refuses characters a screen doesn't show. Text an agent writes for others to read (comments, merge request text, task descriptions) renders with `literalHtml`, which shows raw HTML and Markdown that would show nothing as text; rendered Markdown loads images only from devpad's own origin. `internal/skills` offers the project's skills (Agent Skills `SKILL.md` directories under `.devpad/skills/` and `.claude/skills/`): their names and descriptions go in the system prompt and `load_skill` reads one on the host. The same provider puts the repo's `AGENTS.md` in the system prompt. A review sandbox's skills and `AGENTS.md` come from its merge request's target branch in the canonical repo (`project.ReadAt`, one request for many paths), at the commit the review's diff was read against (`merge_request_reviews.target_sha`, cached in memory by commit), never from the change under review, and a skill never changes what an agent may do (`allowed-tools` is ignored). Neither failing to read `AGENTS.md` nor failing to read skills fails a run; `ChatService.StreamAgent` itself refuses a run in a workspace the user does not own or that is not running (`CheckRunning`), or on a model whose provider the user has no key for. AI settings belong to each user, never the server: provider keys (`user_ai_provider_keys`, sealed with the server's encryption cipher, never sent back to the browser), defaults for built-in agents (`user_ai_agent_defaults`), budgets and the `summarize_file` model (`user_ai_settings`, where an empty model means the cheapest priced model the user has a key for). Every provider request is sent with the key of the user whose run it is, looked up again for each request (`CatalogService.ResolveChatTarget`), so a task's agent and its reviews, automatic ones included, use their owner's key, and removing a key stops that user's runs at their next request. Provider tools run on the host, derive the project from the run's workspace, and never merge, close, push or move a protected branch. A run stops, and fails, when its `domain.Budget` is spent or after 500 model requests; a budget is shared by a run and its sub-agents, which run only on models of their parent's provider (`StartChildRun` refuses another's, and thinking the model doesn't support; `spawn_sub_agent` skips an agent default on one, and `list_available_agents` lists the models a sub-agent can use with prices and efforts), and the user's budgets set one per task (kept on the task with its running `cost_usd`), per review (kept on the review the same way), and per assistant reply. A review of a task's merge request spends from its own budget within the task's (`Budget.Within`), so the task's budget covers its agent and its reviews; a `summarize_file` call spends from the budget of the run that made it. Raising a budget lets what it stopped go on: the task's agent through Start, a review through `ContinueReview`, which resumes it in its own sandbox and transcript. The chat service also writes every provider request to the `ai_usage` ledger (`internal/ai/app/usage_service.go`), one row per request with its project and model. The ledger outlives the request's workspace, run and project, and backs the Usage page (`GET /api/ai/usage`), which shows each user only their own usage.

**Conversation history is server-owned and append-only.** Starting an agent run (`StartAgentRunRequest`) names a conversation and the new user message (text and image attachments); `internal/ai/app` loads the saved history, appends the message once the model stream has opened (so a run that cannot start leaves the conversation as it was), and appends each completed step (assistant turn plus its tool results) as the run produces it. A conversation takes one active run at a time (`ErrConversationBusy`). A task carrying earlier rounds into a new conversation passes them as `Seed`, which only an empty conversation accepts. History is rewritten only to repair tool calls and results that no longer pair up, and to drop reasoning state when the conversation moves to another model. A user turn can carry `DisplayText`, what the user typed when the model is sent something else (a slash command's prompt): titles, previews and the panel show it, providers never see it, and code that copies turns keeps it. The browser only displays run events and answers approvals and questions; it never writes turns. Sub-agent runs (`StartChildRun`) never write to the conversation they are linked to.

**User documentation** — `docs/NN-slug.md` are the pages of devpad's user docs, which `docs/docs.go` embeds and `internal/docs` parses (front matter `title`, `summary`, optional `audience: admin`; every heading below the title ends with an explicit `{#anchor}`), serves at `GET /api/docs` and `GET /api/docs/{slug}` (admin pages only to admins), and offers the assistant in interactive workspaces as `read_devpad_docs`. The app shows them at `/docs` (`DocsView.vue`), and `DocLink` puts a "?" beside the UI each page explains, from `DOC_LINKS` in `frontend/src/utils/docs.ts`. `go test ./internal/docs` fails on a page that doesn't parse, a broken `/docs/...` link between pages, a page linking an admin page, or a `DOC_LINKS` entry whose page or anchor is gone.

**Frontend** is a Vite/Vue 3 app in `frontend/src`. It uses Vue Router guards for setup/auth/admin routing, Pinia stores for shared state, typed API modules under `frontend/src/api`, composables under `frontend/src/composables`, and IDE-specific components under `frontend/src/components/ide`. Vite outputs production assets to `web/dist/`, which `web/embed.go` embeds and serves gzipped with an SPA fallback. Files under `assets/` carry a content hash in their name and are cached as immutable for a year (`TestEmbeddedAssetsAreHashed` fails a build that breaks that), everything else is `no-cache` with an ETag, and a missing `assets/` file is a 404, never the SPA, so a tab from before a deploy reloads at the page it was navigating to (`router/staleBuild.ts`). Monaco is split into its own Vite chunk, and the IDE (`router/views.ts`) is one the app prefetches after sign-in; a navigation waiting on a lazy view's download shows a progress bar (`router/lazyView.ts`).

## Conventions

**Backend**
- Routes use Go's standard `net/http` method-pattern syntax (`mux.Handle("GET /api/workspaces/{id}", ...)`); read path params with `r.PathValue`.
- HTTP handlers return JSON through package-local `writeJSON`/`writeError` helpers and map domain errors to status codes near the handler boundary.
- Auth is session-cookie based (`devpad_session`, or `__Host-devpad_session` when cookies are Secure, i.e. with `--domain` or `--preview-domain`; use `auth.SessionCookieName`). Use `auth.UserFromContext` in authenticated handlers; wrap protected routes with `RequireAuth` or `RequireAdmin` in the central route registration. Besides creating users directly, admins can invite them (`internal/auth/invite_*.go`): a one-time link `/invite#<token>` (the fragment keeps the token out of logs; only its SHA-256 is stored) that creates an account (the invitee picks their username and email, the invite whether it is an admin) and signs it in, never while the browser is signed in to another account. An admin's unused invites go when they stop being an admin: deleting cascades, and a trigger deletes them on demotion, so every path that demotes is covered. Every path that sets a username, email or password checks it with `auth.CleanIdentity` and `auth.ValidatePassword` (`internal/auth/validate.go`, mirrored for passwords by `frontend/src/utils/password.ts`): a username and email are the user's git identity unless they choose another under Settings > Git (`users.git_name`, `git_email`, checked by `auth.CleanGitIdentity`; always read it with `User.GitIdentity`), and the agent refuses one starting with `-`. Once a user has saved one (`git_identity_saved`), `workspace.SyncGitIdentity` writes it into the repo of their running project workspaces and sandboxes, and each start does the same for a stopped one; before that devpad leaves seeded repos alone, and it never touches a standalone workspace's.
- `internal/server/origin.go` refuses state-changing requests and WebSocket upgrades from any origin but the app's own (preview subdomains are same-site, so SameSite cookies don't stop them), and requires JSON bodies under `/api/`. A new non-JSON endpoint must be exempted there explicitly. Every app response carries a Content-Security-Policy (`appContentSecurityPolicy` in `internal/server/server.go`): no framing, and images only from devpad's own origin, `data:` and `blob:` URLs, so no image can send data to another server; anything the app needs from elsewhere is added there, never fetched around it.
- Merge requests call into tasks while holding their own locks (a review requesting changes, a merge closing the task), so the task service never calls the merge request service while holding a task lock: its review hook runs after the lock is released (`announceReview`).
- Wrap lower-level errors with `%w`; do not discard errors except for existing best-effort cleanup paths around Docker resources, SSH injection, sidecars, and agent readiness.
- Database repositories use `context.Context`, parameterized SQL, and `database/sql`; detect a UNIQUE constraint failure with `database.IsUniqueViolation`, never by matching the error text; SQLite is opened with WAL, foreign keys, busy timeout, a single open connection, and immediate transactions.
- Tests are Go `testing` tests colocated as `*_test.go`; use table-style subtests where useful, `t.Helper()` for setup helpers, and in-memory SQLite for repository/service tests.
- Use `internal/container.Manager` and the Docker SDK abstraction; never shell out to the `docker` CLI.

**Agent boundary**
- Code that needs live filesystem, terminal, command, or Git data for a workspace belongs in `cmd/agent` plus a proxy/client path in the host — not only in the Vue frontend.
- Agent requests use the `X-Devpad-Agent-Token` header; `/healthz` and `/api/version` are intentionally unauthenticated.
- The agent cannot call the host. When something inside a workspace needs devpad (like `git push devpad`), the agent queues it and the host polls for it; treat everything queued as untrusted input.

**Frontend**
- Use Vue 3 `<script setup lang="ts">`, strict TypeScript, and the `@/` alias for `frontend/src`.
- Components call API modules or stores instead of constructing endpoint logic inline (except for streaming/WebSocket cases — match the nearby pattern).
- UI styling uses the CSS custom properties in `frontend/src/assets/styles/`: colours in `themes.css`, everything else (spacing, radius, transition, fonts) in `main.css`. Use existing tokens (`--bg-*`, `--text-*`, `--accent`, `--accent-dim`/`-glow`/`-border`, `--hue-*`, `--border-*`) and never a hardcoded colour or a palette's own name: a component must look right in every theme. The older names `themes.css` lists as deprecated (`--bg-primary`, `--bg-surface`, `--text-muted`, `--border-default`, `--accent-blue`, `--accent-rose` and the rest) are only for code not yet moved off them: never use them in new code, and when touching code that does, move it to the current token (`--accent-blue` becomes `--accent` for focus, selection or the primary action, `--hue-blue` where it means blue).
- The UI is flat: a card, tile or panel is a background and a `0.5px` border, like the Git panels, with no inset highlight, bevel, top-edge sheen or drop shadow to lift it. `box-shadow` is only for what floats over the page (`--shadow-popover`, `--shadow-strong` on menus, popovers, modals and toasts), focus rings, and an inset accent bar marking the selected row.
- Themes (Gruvbox Dark, Gruvbox Light, Modern Dark, the default, Modern Light, Nord Dark, Nord Light) are one block of tokens each in `themes.css`, chosen by `data-theme` on `<html>`. `frontend/src/theme/index.ts` applies the theme and builds the Monaco and xterm themes, the tab icon and the browser's `theme-color` from those same tokens (`--editor-*`, `--syntax-*`, `--term-*`), so a colour is only ever defined in CSS. The theme is a user preference (`user_preferences.theme`, NULL until the user picks one so that it follows `DefaultTheme`; Settings > Appearance) that each browser also remembers in `localStorage`, which an inline script in `index.html` applies before the first paint. A new theme needs its block, an entry in `THEMES` (which `ThemeId` is derived from) and in `settings.Themes`, and to pass `npm run check-themes`, which the build runs: it fails when `themes.css` and `THEMES` list different themes, a theme lacks a token another defines or a `color-scheme` of `light` or `dark` (which also picks the editor's light or dark base), a colour the editor, terminal or browser chrome reads is missing or not hex/`rgb()`, or text, hue, syntax and terminal tokens fall short of WCAG contrast on the surfaces they are used on. `TestThemesMatchFrontend` (`internal/settings`) keeps `settings.Themes` and `DefaultTheme` in step with `THEMES` and `DEFAULT_THEME`.

**Documentation** — the docs describe behaviour the user sees, so a change to it (a new feature, a rule, a refusal, a label the docs quote) updates the page under `docs/` that covers it in the same change. Keep pages at the level of concepts and UI labels rather than code, and rename a heading freely but never its `{#anchor}`, which links rely on.

**Build artifacts** — do not include generated artifacts in source changes unless the task is specifically about embedded assets. `web/dist/`, `bin/`, `internal/agentbin/devpad-agent`, and `internal/dockerfile/Dockerfile` are produced by Make targets.
